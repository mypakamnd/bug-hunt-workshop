# Prompt Templates — Test Case Generation (PROJECT: quickshift)

> **PROJECT: quickshift (QuickShift mobile app).** ปรับจาก daywork_app (2026-10-06)
> — โครง QA กลาง (Test Type, Test Data, รูปแบบ Expected Result, การระบายสี, modal)
> ใช้ได้เหมือนเดิม default opener คือ **`เปิดแอป QuickShift`** และใช้คำว่า "แอป"
> แทน "เว็บไซต์"/"หน้าเว็บ"

This is the QA prompt template that the `generate-test-cases` skill reads
before generating. It defines, per Test Type, what **Test Steps**,
**Test Data**, and **Expected Result** should look like. Generate in Thai
unless the source description is clearly in another language.

## Inputs available per row (from the sheet)

- `test_description` — column D, the Test Case name / title / description (required)
- `test_type` — column E, may be pre-filled or empty (generate if empty)
- `precondition` — column G, optional setup context
- `ui` — column K, optional; a description of the UI elements on screen.
  Present on **some** rows only. When present, use it to name UI elements
  precisely in Test Steps and Expected Result.
  **Read EVERY element on that UI and reuse it across sibling cases.** A UI is
  usually attached to only **one** case of a screen (often the first/display
  case, e.g. case 1). When a row has `ui`, enumerate **all** of its elements
  (top-to-bottom, incl. section หัวข้อ and buttons) and treat it as the **source
  of truth for every related case on the same screen/scenario**, even though
  those sibling rows have an empty column K. So if case 1 carries the UI and
  case 2 is the same screen, generate case 2's Steps/Expected from case 1's UI
  elements too — don't guess or omit elements the UI already gave you. Only the
  case-specific action differs between siblings.
- `pre_steps` — the setup prefix for this row, resolved from `pre_steps.json`
  (per tab, and per scenario where configured). **Test Steps must begin with
  these exact lines, numbered, before any case-specific action.** Copy them
  verbatim — do not invent or abbreviate. If empty, start from the case's own
  first step (default opener `เปิดแอป QuickShift`).

## Outputs to generate per row (written to the sheet)

- **Test Type** (col E) — only if the input was empty. Pick one of the 12 types below.
- **Test Steps** (col H) — numbered list `1. ...\n2. ...`.
- **Test Data** (col I) — concrete input values used by the steps (see "Test Data" below).
- **Expected Result** (col J) — numbered list `1. ...\n2. ...`.

**Field-focused cases — "กรอก/เลือกข้อมูลอื่นๆ ครบ" step:** when a case focuses on a
single field (POSITIVE filling it correctly, or NEGATIVE/EDGE leaving it blank /
wrong) and then submits with `กดปุ่ม "บันทึก"`, insert the step
`กรอก/เลือกข้อมูลอื่นๆ ครบ` **right before** the submit step — so the only variable
under test is the focus field and the form is otherwise complete. Skip this for
the full-form case (steps already say "ครบทุกช่อง") and for cases with no submit
(display / modal / observe-only). Example:

```
7. เลือกคำนำหน้า
8. กรอก/เลือกข้อมูลอื่นๆ ครบ
9. กดปุ่ม "บันทึก"
```

> The `Note` blocks in the templates below are **internal guidance** for you,
> the generator. There is no Note column in the sheet — do not write Note back.
> Fold any "Focus แค่ field X" intent into how you write the Steps/Expected.

## Test Data — how to fill column I

Test Data is the concrete values the tester types/selects to run the steps.
It is **not** a restating of the steps.

- POSITIVE / FUNCTIONAL: valid sample values, e.g. `เบอร์โทร: 0812345678`,
  `ชื่อ-นามสกุล: สมชาย ใจดี`, `อายุ: 18`, `คำค้น: สยาม`. If the case has no real input
  (pure display/navigation), leave Test Data empty (`""`).
- NEGATIVE (Input): the field is left blank — `{field}: (เว้นว่าง)`.
- NEGATIVE (Select): the select is not chosen — `{field}: (ไม่เลือก)`.
- NEGATIVE (System-error): all fields valid; the save fails server-side — use valid sample values.
- EDGE Max: a value/file/count just over the limit, e.g. `รายได้: 10,000,001`,
  `ชื่อจริง: 51 ตัวอักษร`, `เบอร์โทร: 08123456789 (11 ตัว)`, `รูปโปรไฟล์: 12 MB`,
  `ประเภทงาน: 6 ประเภท`.
- EDGE Min: a value at/under the floor, e.g. `จำนวนเงิน: 0`, `เบอร์โทร: 0812 (4 ตัว)`.
- EDGE Special/Type: the wrong-kind value/file, e.g. `เบอร์โทร: abcdefghij`, `รูปโปรไฟล์: file.gif`.
- EDGE Number Range: an out-of-range value, e.g. `น้ำหนัก: 1000 (นอกช่วง 0-999)`.
- SECURITY: the payload, e.g. `อีเมล: ' OR '1'='1`, `ช่องค้นหา: <script>alert(1)</script>`.
- Multiple fields: one per line, `field: value`.

Keep Test Data minimal — only the values the steps actually exercise.

# Test Type catalogue

| #   | Type                     | Use when                                                                                                            |
| --- | ------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| 1   | POSITIVE                 | happy path / success                                                                                                |
| 2   | NEGATIVE                 | failure: required input blank / select not chosen / system error on save (3 sub-cases: input, select, system-error) |
| 3   | EDGE CASE (General)      | boundary/limit reference table (all sub-kinds below)                                                                |
| 4   | EDGE CASE (Max)          | over a max: value / length / phone / file size / rows                                                               |
| 5   | EDGE CASE (Min)          | under a min: value (>0) / phone / length                                                                            |
| 6   | EDGE CASE (Special/Type) | wrong char type, wrong file type                                                                                    |
| 7   | EDGE CASE (Number Range) | number outside a valid range (e.g. 0-999)                                                                           |
| 8   | FUNCTIONAL               | core function (save, navigate, …)                                                                                   |
| 9   | SECURITY                 | SQL injection, XSS, auth/data exposure                                                                              |
| 10  | INTEGRATION              | data flow between modules / systems                                                                                 |
| 11  | USABILITY                | UI/UX clarity, navigation                                                                                           |
| 12  | PERFORMANCE              | response time, load                                                                                                 |

The sheet's Test Type column uses the short label written in **UPPERCASE**:
`POSITIVE`, `NEGATIVE`, `EDGE CASE`, `FUNCTIONAL`, `SECURITY`, `INTEGRATION`,
`USABILITY`, `PERFORMANCE`. (The parenthetical sub-kinds above only steer how
you write Steps/Data/Expected — write just the base label in column E.)

# Templates

## 1. POSITIVE (Display / Happy path)

Focus: normal success, correct steps, expected result occurs.

- **Test Steps**: include setup steps first (numbered), then the main action.
- **Expected Result**:
  - Display case: name the UI elements explicitly as a list — **one element per
    bullet** (never group multiple fields on one line with `/`). When a UI
    screenshot/spec is available (column K or an attached image), enumerate the
    **actual** elements top-to-bottom in the order they appear, and include each
    **section header** as its own element written `หัวข้อ "<section>"` (also list
    buttons, e.g. `ปุ่ม "แก้ไข"`). Write the page name **without quotes**
    (`ระบบแสดงผลหน้า<name>`), e.g.
    `1. ระบบแสดงผลหน้าข้อมูลส่วนตัว โดยแสดงรายละเอียดดังนี้\n   - ปุ่ม "แก้ไข"\n   - หัวข้อ "ข้อมูลส่วนตัว"\n   - ชื่อ\n   - นามสกุล`
    The **delete button** on a display page is labelled `ปุ่ม "ลบข้อมูล"` (not
    `"ลบ"`) — use it in both the display element list and the delete-action step
    (`กดปุ่ม "ลบข้อมูล"`).
    An **on-screen message / empty-state text** element is written quoted, like a
    button/header: `ข้อความ "<exact text>"` (e.g. `ข้อความ "ยังไม่มีข้อมูลทักษะและความสามารถ"`) —
    not the prose form `ข้อความแจ้งว่า…`.
  - **Conditional display case** (description has a `กรณี…`, e.g.
    `…กรณียังไม่ได้ยืนยันอีเมล`): list **all** the same UI elements as the base
    display, then **highlight the element the condition is about** by appending the
    condition state in parentheses on that element's bullet, e.g.
    `- อีเมล (ไม่มีสถานะยืนยัน)`. That highlighted bullet is auto-colored **blue**
    `#0000ff` on write. Use the parenthetical **only** for the condition element;
    field-attribute notes like `(ตัวเลือก)` are not highlights and stay black.
  - **Modal case (action modal)**: list the modal's หัวข้อ (title), คำอธิบาย
    (description) and every button, e.g.
    `1. ระบบแสดง modal ยืนยันการยกเลิกการแก้ไขข้อมูล โดยแสดงรายละเอียดดังนี้\n   - หัวข้อ "คุณยังไม่ได้บันทึกข้อมูล ต้องการออกจากหน้านี้หรือไม่?"\n   - คำอธิบาย "หากคุณออกจากหน้านี้ การแก้ไขของคุณจะหายไปและไม่สามารถกู้คืนได้"\n   - ปุ่ม "ยืนยัน"\n   - ปุ่ม "ยกเลิก"`
  - **Display-only modal** (an info modal with no confirm/cancel action — just
    shows content): list หัวข้อ, คำอธิบาย and any content elements (table, list,
    image, …) **without** any ปุ่ม "ยืนยัน"/"ยกเลิก", e.g.
    `1. ระบบแสดงผล modal รายละเอียด BMI โดยแสดงรายละเอียดดังนี้\n   - หัวข้อ "ค่าดัชนีมวลกาย (BMI) คืออะไร?"\n   - คำอธิบาย "คือเป็นมาตรการที่ใช้ประเมินภาวะอ้วนและผอมในผู้ใหญ่ ..."\n   - ตารางเปรียบเทียบค่า BMI`
  - **Cancel/leave-modal outcome case** — the case that tests the _result_ of
    the confirm/cancel modal (the user already pressed ยืนยัน/ยกเลิก), not the
    modal display. Use this terse, fixed one-line wording, by action:
    - Confirm leaving an **add** form (กดยืนยัน on the "ออกจากหน้า" modal):
      `1. ระบบยกเลิกการเพิ่มและออกจากหน้าโดยไม่บันทึก`
    - Confirm leaving an **edit** form (กดยืนยัน on the "ออกจากหน้า" modal):
      `1. ระบบยกเลิกการแก้ไขข้อมูลและออกจากหน้าโดยไม่บันทึก`
    - Cancel a **delete** (กดยกเลิก on the delete-confirm modal — record stays):
      `1. ระบบปิด modal และยกเลิกการลบข้อมูล`
    - **Stay** (cancel-the-cancel — กดยกเลิก on the leave modal to stay on the
      add/edit page): `1. ระบบปิด modal และยังคงอยู่ที่หน้า{เพิ่ม/แก้ไข}... โดยข้อมูลที่{กรอก/แก้ไข}ยังคงอยู่`
      Note: add/edit say **ออกจากหน้า** (separate pages); delete is a modal on the
      list page → **ปิด modal**, no "ออกจากหน้า".
  - **Count / pagination-focused list case** (the description is about *how many*
    items show or which page — e.g. `…มีงานที่สมัคร 15 รายการ`): do **not** enumerate
    the full card. Keep the header count-free (`ระบบแสดงผลหน้า<name> โดยแสดงรายละเอียดดังนี้`)
    and list only the count + paging, e.g. `- รายการจำนวน 15 รายการ` and
    `- pagination 2 หน้า`. Use the exact count from the description; derive pages from
    the page size (e.g. 10/page → 15 items = 2 หน้า). Reserve the full element list for
    the base/empty display case of the screen.
  - Function case: `ระบบบันทึกข้อมูล / ข้อมูลถูกบันทึก`.
  - **Save + toast case**: when a save succeeds and the UI (column K) shows a
    toast, write two lines — confirm the field's data is shown correctly, then
    the toast:
    `1. ระบบบันทึกข้อมูลสำเร็จและแสดงข้อมูลที่{field}ถูกต้อง\n2. ระบบแสดง toast "บันทึกข้อมูลสำเร็จ"`
    (The **system-error / save-fails** case — `กรณีเกิดข้อผิดพลาดของระบบ` — is a
    failure outcome → classify it as **NEGATIVE**, see §2.)
- **Test Data**: valid sample values, or empty for pure display.

## 2. NEGATIVE — Input / Select Field

Vars: `field_name`. Focus: leave `field_name` blank / not chosen; system shows
an error. One type (`NEGATIVE`) with two sub-cases — pick by the field kind.

> ⚠️ **Optional → POSITIVE (case by case):** this is `NEGATIVE` **only when
> `field_name` is required (บังคับ)**. If `field_name` is **optional**
> (ไม่บังคับ / ตัวเลือก), leaving it blank/unchosen still saves successfully —
> reclassify the case as **POSITIVE** and use the save-success Expected Result.
> When an **optional input or select** is left blank and the save succeeds, the
> Expected must state that field renders as **`"-"`** on the display:
> `1. ระบบบันทึกข้อมูลสำเร็จและแสดงข้อมูลที่บันทึกถูกต้องและแสดง{field_name}เป็น "-"\n2. ระบบแสดง toast "บันทึกข้อมูลสำเร็จ"`
> (e.g. `…และแสดงวิดิโอแนะนำตัวเป็น "-"`). Applies to **input/select** fields only
> (a blank **file upload** like รูปภาพ keeps the generic save-success wording).

- **Input sub-case** (ช่องกรอก):
  - **Test Steps**: setup → leave `field_name` blank → submit/click. Focus that field only.
  - **Expected Result** (exactly one line): `1. ระบบแสดง inline validation "โปรดระบุ {field_name}"`
  - **Test Data**: `{field_name}: (เว้นว่าง)`.
- **Select sub-case** (ตัวเลือก):
  - **Test Steps**: setup → do not select `field_name` → submit/click.
  - **Expected Result** (exactly one line): `1. ระบบแสดง inline validation "โปรดเลือก {field_name}"`
  - **Test Data**: `{field_name}: (ไม่เลือก)`.
- **Gated-submit sub-case** (a modal/form whose submit button stays **disabled**
  until a required choice/detail is provided — e.g. a cancel-reason modal where
  ปุ่ม "ยืนยัน" is disabled until a reason is picked, and if the chosen option is
  "อื่นๆ" until its detail is filled). Do **not** use inline validation here; the
  system simply blocks the click:
  - **Expected Result** (one line):
    `1. ระบบไม่อนุญาตให้กดปุ่ม "{submit}" เนื่องจากยังไม่ได้{เลือก.../กรอก...}`
  - Applies to both "ไม่เลือก/ไม่ระบุ" and "เลือกอื่นๆ แต่ไม่กรอกรายละเอียด".
  - In the modal's display case, mark that button `ปุ่ม "{submit}" disable`.
- **System-error sub-case** (เกิดข้อผิดพลาดของระบบ — form is filled correctly but
  the backend/server fails on save; not tied to any one field):
  - **Test Steps**: setup → fill every field correctly → `กดปุ่ม "บันทึก"`.
  - **Expected Result** (two lines):
    `1. ระบบบันทึกข้อมูลไม่สำเร็จ\n2. ระบบแสดง toast "เกิดข้อผิดพลาด ไม่สามารถบันทึกข้อมูลได้, โปรดลองอีกครั้งในภายหลัง"`
  - **Test Data**: valid values for all fields (the failure is simulated server-side).

## 3. EDGE CASE — General (boundary / limit reference)

`EDGE CASE` covers boundary, limit, wrong-type and out-of-range input. Column E
always reads `EDGE CASE`; the sub-kind only steers Steps/Data/Expected. Use this
table for the **exact** one-line Expected Result wording (inline validation,
toast, or a hard block):

| Sub-kind                | Example case              | Expected Result                                                                                         |
| ----------------------- | ------------------------- | ------------------------------------------------------------------------------------------------------- |
| Min number (≤ 0)        | จำนวนเงิน ≤ 0             | `ระบบแสดง inline validation "โปรดระบุมากกว่า 0"`                                                        |
| Min phone (< 10 digits) | เบอร์โทร < 10 ตัว         | `ระบบแสดง inline validation "เบอร์โทรศัพท์ไม่ถูกต้อง"`                                                  |
| Max number value        | รายได้ > 10,000,000       | `ระบบแสดง inline validation "{field}ต้องไม่เกิน {max}"` (เช่น `รายได้ที่คาดหวังต้องไม่เกิน 10,000,000`) |
| Max text length         | ชื่อจริง > 50 ตัวอักษร    | `ระบบแสดง inline validation "{field}ต้องมีความยาวไม่เกิน {max} ตัวอักษร"`                               |
| Max phone digits        | เบอร์โทร > 10 ตัว         | `ระบบไม่อนุญาตให้กรอกเบอร์โทรเกิน 10 หลัก`                                                              |
| Max file size           | ไฟล์ > 10 MB              | `ระบบแสดง toast "ไฟล์ขนาดใหญ่เกินไป (สูงสุด 10 MB)"`                                                    |
| Wrong file type         | ไฟล์ ≠ .png/.jpg/.jpeg    | `ระบบไม่อนุญาตให้ผู้ใช้งานอัปโหลดรูปโปรไฟล์เป็นไฟล์อื่นนอกเหนือจาก .png, .jpg หรือ .jpeg`               |
| Max rows / items        | เพิ่มประเภทงาน > 5 ประเภท | `ระบบไม่อนุญาตให้กดปุ่ม "เพิ่มประเภทงาน"`                                                               |
| Wrong char type         | กรอกเบอร์โทรเป็นตัวอักษร  | `ระบบไม่อนุญาตให้ผู้ใช้งานกรอกเบอร์โทรศัพท์เป็นตัวอักษร`                                                |
| Number range (over)     | น้ำหนัก > 999             | `ระบบแสดง inline validation "น้ำหนักต้องอยู่ระหว่าง 0 ถึง 999"`                                         |
| Number range (under)    | น้ำหนัก ≤ 1 (นอกช่วง)     | `ระบบแสดง inline validation "น้ำหนักต้องอยู่ระหว่าง 0 ถึง 999"`                                         |

Sections 4–7 expand the common ones. Notes: number **value** caps have no "ตัว"
and keep the comma (`10,000,000`); a **digit/length** cap uses "ตัว"/"ตัวอักษร";
phone, file-size, file-type and max-rows are **hard blocks/toasts**, not the
generic "ต้องไม่เกิน" wording.

## 4. EDGE CASE — Max (value / length / phone / file size / rows)

Vars: `field_name`, `max`. Pick the wording by **what** is capped:

- **Test Steps**: setup → push `field_name` just over `max` (or upload/add one too many) → submit.
- **Expected Result** — choose by kind:
  - Numeric **value** (เงิน/รายได้): `1. ระบบแสดง inline validation "{field_name}ต้องไม่เกิน {max}"` (เช่น `รายได้ที่คาดหวังต้องไม่เกิน 10,000,000` — มี comma, ไม่มี "ตัว")
  - Text **length**: `1. ระบบแสดง inline validation "{field_name}ต้องมีความยาวไม่เกิน {max} ตัวอักษร"`
  - **Phone digits** (hard block): `1. ระบบไม่อนุญาตให้กรอกเบอร์โทรเกิน 10 หลัก`
  - **File size** (toast): `1. ระบบแสดง toast "ไฟล์ขนาดใหญ่เกินไป (สูงสุด 10 MB)"`
  - **Max rows/items** (add button blocked): `1. ระบบไม่อนุญาตให้กดปุ่ม "เพิ่ม{field_name}"` (เช่น `เพิ่มประเภทงาน`)
- **Test Data**: value/file/count just over the limit (e.g. `จำนวนเงิน: 10,000,001`, `รูปโปรไฟล์: 12 MB`, `ประเภทงาน: 6 ประเภท`).

## 5. EDGE CASE — Min (value / phone / length)

Vars: `field_name`, `min`.

- **Test Steps**: setup → enter `field_name` at/under the floor → submit.
- **Expected Result** — choose by kind:
  - Numeric **value** floor (must be > 0): `1. ระบบแสดง inline validation "โปรดระบุมากกว่า 0"`
  - **Phone** min length (< 10 digits): `1. ระบบแสดง inline validation "เบอร์โทรศัพท์ไม่ถูกต้อง"`
  - Generic **length** floor: `1. ระบบแสดง inline validation "{field_name}ต้องไม่น้อยกว่า {min} ตัว"`
- **Test Data**: a value at/under the floor (e.g. `จำนวนเงิน: 0`, `เบอร์โทร: 0812 (4 ตัว)`).

## 6. EDGE CASE — Special Characters / wrong kind of input

Vars: `field_name`, `special_chars`.

- **Test Steps**: setup → enter `field_name` with `special_chars` → submit.
- **Expected Result** (pick the system's real behaviour, matching F03_On_Boarding):
  - Letters typed into a numeric field: `1. ระบบไม่อนุญาตให้ผู้ใช้งานกรอก{field_name}เป็นตัวอักษร`
  - Wrong file type uploaded (e.g. profile picture / รูปโปรไฟล์):
    `1. ระบบไม่อนุญาตให้ผู้ใช้งานอัปโหลดรูปโปรไฟล์เป็นไฟล์อื่นนอกเหนือจาก .png, .jpg หรือ .jpeg`
    (general form: `1. ระบบไม่อนุญาตให้ผู้ใช้งานอัปโหลด{field_name}เป็นไฟล์อื่นนอกเหนือจาก .png, .jpg หรือ .jpeg`)
  - reject (generic): `1. ระบบแสดง inline validation "{field_name}ต้องเป็นข้อมูลที่ถูกต้อง"`
  - accept: `1. ระบบ accept ข้อมูล และบันทึกได้`
- **Test Data**: the special-character string, e.g. `น้ำหนัก: abc`, `รูปโปรไฟล์: file.gif`.

## 7. EDGE CASE — Number Range

Vars: `field_name`, `min_value`, `max_value`, `test_value` (out of range).

- **Test Steps**: setup → enter `field_name` = `test_value` (outside range) → submit.
- **Expected Result** — use ONE unified message for BOTH below-min and above-max
  (matches F03_On_Boarding, e.g. both `-1` and `1000` → "ต้องอยู่ระหว่าง 0 ถึง 999"):
  `1. ระบบแสดง inline validation "{field_name}ต้องอยู่ระหว่าง {min_value} ถึง {max_value}"`
- **Test Data**: `{field_name}: {test_value}` (e.g. `น้ำหนัก: -1` or `น้ำหนัก: 1000`).
